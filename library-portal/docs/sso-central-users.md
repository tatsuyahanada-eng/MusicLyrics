# 共通ユーザーデータベースと SSO — 権限は損なわれるか

**結論：損なわれません。** ただし条件が 1 つあります。
**認証（誰か）は共通化し、認可（このアプリで何ができるか）はアプリ単位で持つ**こと。
ここを混ぜると、あるアプリの管理者が全アプリの管理者になってしまいます。

実際に共通ユーザーDBを構築し、ライブラリポータルをそこへ接続して検証しました（結果は §4）。

---

## 1. 役割分担

| | 置き場所 | 内容 |
|---|---|---|
| **認証**（誰か） | 共通ユーザーDB `auth_users` | ログインID・パスワード・氏名・在籍状態 |
| **認可**（何ができるか） | 共通ユーザーDB `auth_app_roles`（アプリ単位の行） | `library` では管理者、`expense` では閲覧のみ |

```
                    ┌─────────────────────────────┐
                    │   共通ユーザーDB (welsys_auth)   │
   ログイン ────────>│  auth_users     … 本人確認      │
                    │  auth_app_roles … アプリ別権限   │
                    └─────────────┬───────────────┘
                app_key='library' │ app_key='expense' │ …
                    ┌─────────────▼──────┐  ┌─────────▼──────────┐
                    │ ライブラリポータル      │  │ 交通費精算アプリ      │
                    │ 業務データは各アプリのDB │  │ 業務データは各アプリのDB│
                    └────────────────────┘  └────────────────────┘
```

権限を `auth_app_roles(app_key, user_id, role)` の 1 行として持つため、
**同じ人が「ライブラリでは管理者・別アプリでは閲覧のみ」**を自然に表現できます。
`role` の語彙（admin / viewer など）はアプリごとに自由に決められます。

> 権限をアプリ側の DB に置く方式（`lp_users.role` のまま）も可能ですが、
> 利用者ごとの権限を一箇所で見渡せる共通DB方式を推奨します。
> 本アプリは **両方に対応**しており、`config.php` の 1 行で切り替わります。

---

## 2. 実装（本アプリ側の対応は完了しています）

`includes/config.php`：

```php
'auth_mode'    => 'central',        // 'local'（単独運用）/ 'central'（共通ユーザーDB）
'app_key'      => 'library',        // 共通DB上でのこのアプリの識別子
'default_role' => 'none',           // 権限行が無い利用者の扱い：'viewer' か 'none'（ログイン拒否）
'auth_db_host' => 'mysqlXXX.db.sakura.ne.jp',
'auth_db_name' => 'アカウント名_auth',
'auth_db_user' => 'アカウント名',
'auth_db_pass' => '…',
```

- 供給元の切り替えは `includes/auth_provider.php` に集約しています。
  画面・API 側のコード（`is_admin()`、`api_require_admin()` など）は**一切変更していません**。
- 移行用 SQL は `sql/migrate_local_to_central.sql`、共通DBの DDL は `sql/schema_central_auth.sql` です。
- `default_role`
  - `'viewer'` … 権限行が無い人も閲覧はできる（社内へ広く公開する場合）
  - `'none'` … 権限行が無い人はログイン不可（利用者を限定する場合。**推奨**）

### 設定画面の挙動の違い

| 操作 | `local` | `central` |
|---|:--:|:--:|
| このアプリでの権限変更（管理者／閲覧のみ／権限なし） | ○ | **○** |
| アカウントの新規作成・削除・停止・パスワード再設定 | ○ | ×（共通の利用者管理へ集約） |

`central` では利用者一覧に共通DBの全員が並び、各行で**このアプリの権限だけ**を切り替えます。
「権限なし」を選ぶと `auth_app_roles` の行が削除され、そのアプリだけ使えなくなります。

## 3. シングルサインオン（ログイン状態の共有）

共通ユーザーDBは「同じID・同じパスワードで各アプリにログインできる」状態までを実現します。
**「一度ログインすれば他のアプリでもログイン画面が出ない」**を実現するには、
セッションの共有方式を別途決める必要があります。さくらのレンタルサーバでの現実的な選択肢は次の 2 つです。

### 方式A：共通ログインアプリ ＋ 共有セッションテーブル（推奨）

1. `auth.example.co.jp/login`（または `/auth/`）に**共通ログイン画面**を 1 つ用意
2. ログイン成功時、`auth_sessions` に乱数の `session_id` を記録し、
   **クッキーのドメインを親ドメイン**（`.example.co.jp`）にして発行
3. 各アプリは、そのクッキーの `session_id` で `auth_sessions` を照会して本人を判定
4. ログアウトは `auth_sessions.revoked_at` を更新 → **全アプリで即座に無効**

- 必要なテーブルは `sql/schema_central_auth.sql` の `auth_sessions` に用意済みです。
- 本アプリ側の改修は `includes/auth_provider.php` に
  「クッキー → session_id → user_id」の判定を 1 関数追加するだけで済みます
  （権限判定 `resolve_role()` はそのまま使えます）。
- **条件**：全アプリが同一ドメイン配下（サブドメインまたはサブディレクトリ）であること。

### 方式B：ワンタイムチケット（別ドメインが混在する場合）

未ログインなら共通ログイン画面へ飛ばし、認証後に一度だけ有効な署名付きトークンを付けて
アプリへ戻し、アプリ側で検証してから自前のセッションを開始する方式です。
別ドメインでも成立しますが、実装量は方式Aより増えます（OpenID Connect の簡易版に相当）。

### どちらでも変わらないこと

**権限判定は各アプリが毎リクエスト、共通DBの `auth_app_roles` を見て行います。**
SSO はあくまで「本人確認の使い回し」であり、権限まで持ち回るわけではありません。
これが「共通化しても権限が損なわれない」理由です。

## 4. 検証結果（実機確認）

共通ユーザーDB（`auth_users` / `auth_app_roles`）を実際に構築し、
ライブラリポータルを `auth_mode = 'central'` で接続して確認しました。

利用者の設定：

| 利用者 | library での権限 | 別アプリ(expense)での権限 |
|---|---|---|
| 花田（hanada.t） | 管理者 | 閲覧のみ |
| 佐藤（sato.m） | 閲覧のみ | — |
| 田中（tanaka.r） | 権限行なし | — |
| 井上（inoue.y） | 権限行なし | **管理者** |

| # | 確認項目 | 結果 |
|---|---|---|
| 1 | 共通DBのIDとパスワードでログインできる | ○ |
| 2 | 管理者（花田）に登録ボタン・設定画面が表示される | ○ |
| 3 | 管理者が更新履歴を登録でき、対応者として**共通DBのID**が記録される | ○ |
| 4 | 閲覧のみ（佐藤）に登録ボタンが出ない | ○ |
| 5 | 閲覧のみが `settings.php` を直接開く | **403** |
| 6 | 閲覧のみが書き込みAPIを直接叩く | **403** |
| 7 | **別アプリの管理者（井上）がライブラリで管理者にならない** | ○（権限の漏れなし） |
| 8 | ライブラリの権限変更が `expense` の権限に影響しない | ○（別行のため無関係） |
| 9 | 権限変更が、ログイン中の利用者に次の画面遷移で反映される | ○（閲覧のみ→管理者を即確認） |
| 10 | `default_role='none'` で権限行の無い利用者はログイン拒否 | ○（メッセージ表示） |
| 11 | ログイン中の利用者の権限を取り消すと、次の遷移でログアウト | ○ |
| 12 | 共通DBでアカウントを停止すると、ログイン中でも次の遷移でログアウト・再ログイン不可 | ○ |
| 13 | 最後の管理者の降格・権限取消を拒否 | ○ |
| 14 | 自分自身の権限変更を拒否 | ○ |
| 15 | `auth_mode='local'`（現行）に戻しても従来どおり動作 | ○ |

権限変更の履歴は各アプリの `lp_audit_log` に
`role.assign / role.revoke（app=library role=admin）` として記録されます。

## 5. 注意点（共通化するなら決めておくこと）

1. **ログインIDの一意性** — 全社で重複しない体系（メールアドレス or 社員番号）を先に決めてください。
   後から統合すると、同じ人が複数IDを持つ状態の解消が大変です。
2. **退職・異動の反映** — `auth_users.is_active = 0` にすれば全アプリで即座にログイン不可になります。
   運用の入口をここに一本化してください。
3. **パスワードポリシー** — 共通DBに集約されるため、影響範囲も全アプリに広がります。
   桁数・有効期限・ロック条件は共通ログイン側で一元管理するのが安全です。
4. **共通DBの可用性** — 共通DBが落ちると全アプリがログインできません。
   バックアップと、（可能なら）参照専用の予備を検討してください。
5. **アプリ側のIDの持ち方** — 業務データに利用者IDを保存する場合は、
   **共通DBのIDを保存し、外部キー制約は張らない**でください
   （別データベースをまたぐ制約は張れないためです）。本アプリはこの形に修正済みです。
6. **権限名の設計** — アプリごとに `role` の語彙が違って構いませんが、
   共通の利用者管理画面で選択肢を出すために `auth_apps.roles_json` に定義しておくと運用が楽になります。

## 6. 移行手順（現行のライブラリポータルを共通DBへ）

1. 共通DBを作成し、`sql/schema_central_auth.sql` を実行
2. `sql/migrate_local_to_central.sql` で既存利用者と権限を移行
   （パスワードのハッシュはそのまま移せるため、利用者の再設定は不要です）
3. `includes/config.php` の `auth_mode` を `'central'` に変更し、共通DBの接続情報を記入
4. 管理者・閲覧者それぞれで動作確認
5. 問題なければ、アプリDBの `lp_users` を削除（数週間はロールバック用に残すことを推奨）
