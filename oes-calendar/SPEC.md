# OES入替作業APP 仕様書 (SPEC.md)

GoogleカレンダーへOES入替作業の予定を登録するためのWebツールの仕様書。

## 0. 前提：複数人で使うアプリである

このアプリは**会社の複数の担当者が、それぞれ自分の端末で使うこと**を前提に設計する。
「一人用ツール」として単純化しないこと。

- **設定は全員が同じ内容を使う。** 業態・時間帯・定型文・よく使う文などは、index.html と同じ場所に置く
  **`settings.json` 1ファイル**に保存し、全員がそこから読み込む（5.6節）。
- **設定を変更できるのは管理者だけ。** 設定タブは管理者パスワードでロックする（5.0節）。
- **アプリ内に「担当者」という概念は持たない。** 誰が使っても同じ画面・同じ設定で動く。
- **作業当日の予定は、各自が自分のGoogleカレンダーの説明文をコピーして貼り付ける**のが標準の使い方
  （4.1節）。Googleカレンダーからの直接読み込みは、利用者ごとにカレンダーが異なり共有設定と噛み合わないため停止した。

## 1. 概要

- 本体は1つのHTMLファイル (`index.html`)。外部ライブラリ・CDN・ビルドツールは使わない
  （プレーンなHTML/CSS/JavaScript、画面に使うロゴ・写真・スプラッシュのアイコンはdata URIで内包）。
- サーバーにFTPでアップロードして使用。必要に応じて `.htaccess` でBasic認証。
- **PWA（ホーム画面に追加してアプリのように使える）対応。** Androidで独立したアプリとして登録させるため、
  マニフェスト（`manifest.json`）とService Worker（`sw.js`）、アイコン（`icon-*.png`）は
  **`index.html` と同じ階層に実ファイルとして配置する**（2.1節）。アイコンはマルチプリンター（SEIKO）の写真に「OES」バッジを重ねたもの。
- **管理者パスワードは `index.html` に書かない。** サーバー上の設定ファイル（`config.php` または `config.json`）
  から読み込む（5.0節）。
- **起動時にスプラッシュを表示する。** OESアイコン＋アプリ名「OES入替作業APP」＋ウェルシス株式会社のバッジを
  1.2秒表示してフェードで消す。`pointer-events:none` で操作は妨げない。
- 画面は3タブ構成（カレンダー／作業当日／設定）。カレンダーは**質問形式（ウィザード）**で、
  ①業態と稼働件数 → ②日付・時刻・店舗名・住所をまとめて入力 → ③一覧確認・Googleカレンダーへ登録、の
  3ステップを1画面で完結する。各ステップには進捗バッジと「次へ」の案内を出し、いま何をすればよいかが
  分かるようにする（3.6）
  (旧版の「登録リスト」タブは「カレンダー」タブに統合)。パソコン・スマートフォン両対応、スマホでの利用を重視したコンパクトな余白。
- 配色は「濃い灰色（メイン）× 濃い赤（アクセント）」のバイカラー（両色ともはっきり見えるトーンにする。詳細は2節）。
- 月めくり式のカレンダーグリッドは廃止した。件数ぶんの行にそれぞれ日付入力（ネイティブの日付ピッカー）を
  持たせることで、1件目と2件目で違う日付を選べるようにしている。
- 予定データはサーバーに保存しない。**設定のみ** サーバー上の `settings.json`（1か所）に保存し、
  全員がそれを読み込んで使う。ブラウザの `localStorage` は、共有設定を読めなかったときの控え。
- 操作マニュアルは `manual.html`（ヘッダー右上のリンクから別タブで開く）。

## 2. デザイン

- タイトル: 「OES入替作業APP」／ サブ: 「Googleカレンダー 一括登録ツール」
- 「カレンダー」画面の①カード（「どこの業態を、何件まわりますか？」）のタイトル横にマルチプリンター（SEIKO）、
  「作業当日」画面のタイトル横にマルチステーションの画像を、小さく（高さ34〜38px、`mix-blend-mode:multiply`）添える。
  data URIで内包。ファイル名は `device-printer.jpg` / `device-kitchen.jpg`。
- **配色は「濃い灰色×濃い赤」のバイカラー。** メインの濃い灰色 `#33383D`（`--blue`）とアクセントの
  濃い赤 `#86100C`（`--sky`）の2色を軸にする。**色の変遷**（新しく変える際は必ず把握すること）:
  「青×空色」→「濃紺`#003DA5`×オレンジ`#F2600D`」→「濃紺×オレンジ（少し暗め`#E25908`）」→
  **「濃い灰色`#33383D`×濃い赤`#86100C`」（現在。利用者が「血圧警告」風の画像を色の参考として添付し、
  それに合わせて変更）**。変数名`--blue`/`--sky`は歴史的な名残で、現在の実際の色は青でもオレンジでもない。
  ヘッダー背景・選択中タブは濃い灰色×濃い赤の2色、カード見出しの番号丸（`.step`）や `.btn-sub` はアクセントの
  濃い赤、カード見出し帯・淡色ボタン・枠線などの薄色部分（`--blue-l` `--blue-l2` `--line` `--line-w`）は
  アクセント寄りの薄いピンク系トーンにする。背景 `#F6F4F0`。削除ボタンの赤・自動生成タグの緑・手動編集タグの
  琥珀色は意味付きの色としてそのまま残す（バイカラーの対象外。**ただし削除ボタンの赤とアクセントの
  濃い赤は別の色**）。
  **2色は滑らかにぼかさず、斜めにくっきり分かれた面にする**（同じ色を隣接する2つの色停止点に置く
  `linear-gradient(135deg,var(--blue) 0%,var(--blue) 62%,var(--sky) 62%,var(--sky) 100%)` の書き方。
  利用者の指定により、以前の自然なグラデーションでのぼかしから変更）。
  ただし**文字自体をこの2色でグラデーション表示するのは行わない**（1文字の途中で色が変わって読みにくいため。
  スプラッシュのアプリ名は単色（濃い灰色）で表示する）。
  **配色を変える際は`:root`の変数だけでなく、ハードコードされた色（`.header-sub`・`.field > label`・
  `.btn-ghost`・`.pb-edit`・`#toast`・`.il-note`・スプラッシュの背景ウォッシュ・`.slot-edit`や`.ph`等の
  枠線・淡色背景・`manifest.json`の`theme_color`・PWAアイコン・`manual.html`の`:root`）も
  必ず一緒に洗い出して更新する。
- フォント: Hiragino Sans / Noto Sans JP / Meiryo 系。
- **全体にコンパクトな余白を採用する**（スマホでの利用が中心のため）。body・カード・見出しの padding は必要最小限にし、
  ボタン/入力欄の `min-height` は 34〜38px を目安にする（タップ領域34px以上は死守。それ未満に削らない）。
- レスポンシブ: 600px / 900px をブレークポイントとする（入力欄の文字サイズ・列数のみ変化。カレンダーは常に1か月）。
  - 900px以上: 登録リストのカードは3列、入力欄は13.5px。
  - 600px以上900px未満: カードは2列。
  - 600px未満: 1列。入力欄は16px（iOSの自動ズーム防止）、タップ領域は34px以上。
- 横スクロールは発生させない（幅の広い表は `overflow-x:auto` の中に入れる）。

### 2.1 PWA（ホーム画面への追加）

- `<link rel="manifest" href="manifest.json">` で**実ファイル**を参照する。
  data URIのマニフェストではAndroidでWebAPKが生成されず、**Chromeのマークが重なったただのショートカット**に
  なってしまうため、data URIに戻さないこと。
- マニフェスト（`manifest.json`）の内容: `id:"./"`、`name`/`short_name`「OES入替作業APP」/「OES入替作業」、
  `start_url:"./index.html"`、`scope:"./"`、`display:"standalone"`、`theme_color:"#003DA5"`、
  `background_color:"#F6F4F0"`、`orientation:"portrait-primary"`、`lang:"ja"`、
  `icons`（`icon-192.png`・`icon-512.png` が `purpose:"any"`、`icon-512-maskable.png` が
  `purpose:"maskable"`）。**アイコンは実URLで書き、`index.html` と同じ階層に置く**
  （WebAPK生成時にサーバーから取得されるため。`assets/` の中だけに置くと、`assets/` を
  アップロードし忘れた環境でアイコンが取得できず、アイコンの無いショートカットになる）。
  マニフェストのファイル名は **`.webmanifest` ではなく `.json`** にする
  （未知の拡張子として扱うサーバーがあるため）。
- `sw.js`（Service Worker）を `navigator.serviceWorker.register('sw.js')` で登録する。`file://` では登録しない。
  方式はネットワーク優先（FTPで差し替えたら次に開いたときすぐ反映される）＋オフライン時のみキャッシュ。
  `settings.json` `config.json` `*.php` は共有設定が古くならないよう**キャッシュしない**。
- **Androidで独立したアプリ（WebAPK）として登録される条件**（1つでも欠けるとショートカット扱いになる）:
  ①`https://` 配信 ②実ファイルのマニフェスト ③`id`/`start_url`/`scope`/`display:standalone` ④192・512・
  maskableのアイコンが取得できる ⑤fetchハンドラを持つService Workerが登録されている。
  すでにショートカットとして追加済みの場合は、一度削除してから追加し直す必要がある。
- アイコンは `assets/device-printer.jpg`（マルチプリンター写真）を土台に、中央下寄りに**バッジ
  （現在は濃い灰色`#33383D`。バイカラーの色が変わったら合わせて変える）**で白太字の「OES」の文字を
  重ねたもの。プリンターの写真自体は変更しない（利用者の指定：写真部分はそのまま、バッジの配色だけ変更）。
  **バッジの文字はオレンジではなく白にする**（オレンジ文字は濃色の上で見づらいという利用者の指摘により変更）。
  マスカブル版は安全領域（中心80%）に収まるよう画像とバッジを一回り小さく配置する。
- `<link rel="apple-touch-icon">`（180x180）と `apple-mobile-web-app-*` 系メタタグでiOSのホーム画面追加にも対応。
- アイコン生成手順は本仕様書の範囲外。再生成する場合は `assets/device-printer.jpg` を土台に、中央下へ角丸の
  バッジ（現在`#33383D`。バイカラーの現在値に合わせる）を描き、白のボールド文字で「OES」を重ねる
  （オレンジ文字ではない。上記の通り）
  （192/512/180/512-maskableの4サイズ。180はindex.html内のapple-touch-icon用data URIとして埋め込む）。

## 3. 画面1: カレンダー登録（質問形式のウィザードで1画面完結）

旧版は「カレンダーで選ぶ」→「登録リスト」の2タブに分かれ、次に複数日をまとめて選んでから
共通の内容を流し込む方式だった。**今版は、①業態と稼働件数を選ぶ → ②件数ぶんの日付・時刻・店舗名・
住所をまとめて入力する → ③一覧で確認してGoogleカレンダーへ登録、という3ステップの質問形式
（ウィザード）にした。** この順番は利用者が明示的に指定したものであり、1つの入力欄にまとめ直さないこと。
月をめくる形のカレンダーグリッドは廃止し、1件ごとにネイティブの日付ピッカーを持たせることで、
同じ日に複数件でも、1件目は10/1・2件目は10/10のように別の日でも、自由に選べるようにしている。

**②はかつて「日付と時刻を選ぶ」→「店舗名と住所を入力する」の2ステップに分かれていたが、
「1件目で日付も店舗名、住所も入力できた方が入力しやすい。日付時間だけ先にして、あとで店舗名だと
ごちゃごちゃになる」という利用者の指摘により、1件ごとに日付・時刻・店舗名・住所をまとめて
1か所に入力する1ステップへ統合した（旧④の登録リストは③に繰り上げ）。この統合を、日付だけを先に
まとめて選ぶような分割方式に戻さないこと。**

**このアプリはまず「Googleカレンダーへ予定を登録するツール」として成立していることを最優先とする。**
作業当日タブ（4章）は、その上に載る補助機能という位置づけ。

### 3.1 ①業態と稼働件数を選ぶ

- `#w-gyotai`（業態）／`#w-count`（稼働件数、1〜30件から選ぶ）の2項目のみ。
  **担当者に関する項目は無い**（アプリ全体で担当者の概念を廃止済み）。
  業態プルダウンの並び順は設定画面での並び順（5.1節）に従う。
- 選んだ業態に登録されている時間帯を、参考情報として`#w-time-hint`に表示する
  （例:「この業態の時間帯: 午前 (AM) 08:30〜09:30 ／ 午後 (PM) 14:30〜15:30」）。②では1件ずつ自由な時刻に変えられる。
- **稼働件数**は「この業態で何件まわるか」を表し、②に並ぶ入力行の数を決める。

### 3.2 ②日付・時刻・店舗名・住所をまとめて入力

- `#item-rows` に稼働件数ぶんの行（`.item-row`、`data-idx`で0始まりの通し番号）が並ぶ。
- 各行は1件分の **日付**（`<input type="date">`）、**開始・終了の時刻プルダウン**（`.dr-start` / `.dr-end`）、
  **店舗名**（`.sr-tenpo`）、**住所（任意）**（`.sr-addr`。ブラウザの自動入力を防ぐため `autocomplete="off"`）を
  1つのカード内にまとめて持つ。同じ日を複数件選んでも、別々の日を選んでもよい。住所はGoogleカレンダーの
  「場所」に入る。
- 時刻の初期値は、選んでいる業態の1つめの時間帯（`wizDefaultTimes()`）。業態を変えると各行の時刻を
  その業態の時刻に入れ替える（`applyGyotaiTimesToRows()`）。終了が開始より前になったら自動で揃える（`fixRowTimes()`）。
- **どの定型文を使うかは、開始時刻に一番近い時間帯から決める**（`slotNearestTime()`）。
  例: すき家で 14:30 を選べば「午後 (PM)」の定型文が使われる。午前/午後のトグルは廃止した。
- 稼働件数を変えると行が過不足なく増減する。既に入力済みの行の内容は保持される。
- **1件目の開始・終了時刻を変更すると、2件目以降にも同じ時刻がそのままコピーされる**
  （`applyFirstRowTimeToOthers()`。毎回同じ時刻を入力し直さなくてよいようにする利用者からの指定）。
  件数を増やして行が新しく増える場合も、1件目が入力済みならその時刻を初期値として使う
  （`firstRowTimesOrDefault()`）。2件目以降は個別に上書きしてよいが、1件目をまた変更すると
  全行に再度上書きされる。
- 「このN件を登録リストへ」（`submitStoreRows()`）を押すと、**日付が選ばれている行だけ**を登録リストに
  追加する。日付未選択の行は黙ってスキップし、スキップした件数があればトーストで知らせる。
  店舗名・住所は空欄のまま登録してもよい（あとから③で編集できる）。店舗名は登録時に語尾へ「店」を自動補完する。
- 登録が完了すると、②の入力は空に戻る（行数＝稼働件数はそのまま維持する）。
- 1件も日付が選ばれていない状態で押した場合はトーストで案内し、何も登録しない。

### 3.3 ③一覧で確認してGoogleカレンダーへ登録（登録リスト）

- 1件＝1カード。**既定は折りたたみ表示**で、見出し行に「番号・要約（日付／時刻／業態／店舗名）・
  『登録』ボタン・開閉の矢印」だけを表示する（`toggleEntry(id)`で開閉）。稼働件数が多くても
  一覧が縦に伸びすぎないようにするための設計であり、全展開表示には戻さないこと。
- 見出しをタップして開くと、日付／業態／時間帯／開始／終了／店舗名／住所／説明文を個別に編集できる
  （複製・削除ボタンもここに現れる）。
- 業態を変えると、その業態の先頭の時間帯・時刻・定型文に切り替わる。
- 説明文は既定で「定型文から自動生成」。手入力すると「手動で編集」に変わり自動更新を停止する。「定型文に戻す」で再生成。
- ツールバー: Googleカレンダーで順番に登録／ICSファイルで一括取込／空の行を追加／全て削除。
- 並び順は日付→開始時刻の昇順（`sortEntries()`。追加のたびに実行）。
- 件数はタブの「📅 カレンダー」バッジに表示する（`#list-count`。旧版の「📋 登録リスト」タブ廃止に伴い移設）。

### 3.4 Googleカレンダーへの一括登録（2通り、どちらもこの画面のツールバーから）
- **Googleカレンダーで順番に登録** — モーダルで「◯件目 / 全◯件」を表示し、「開く」を押すたびに
  1件ずつ新しいタブで開く（ポップアップブロック対策）。「とばす」で1件スキップ、「中止」で終了。ESCキーでも閉じる。
- **ICSファイルで一括取込** — `oes-YYYYMMDD.ics` をダウンロードし、GoogleカレンダーのUI
  （設定→インポート／エクスポート）で確認なしにまとめて取り込む。RFC5545準拠。`VTIMEZONE`
  （Asia/Tokyo, +0900固定）を含み、`DTSTART;TZID=Asia/Tokyo:` 形式。行は75オクテットで折り返す
  （マルチバイト文字を壊さないよう文字単位で判定）。BOM付きUTF-8。

## 4. 画面2: 作業当日

作業当日に、その日の作業内容を確認し、Google Chat へ貼り付ける連絡文をコピーするための画面。
**Google Chat への自動送信は行わない**（コピー → 手動で貼り付け → 送信）。入店・中間・退店の
連絡は、入力する手間をできるだけ減らし、コピー＆貼り付けだけで済むことを目的にしている
（②の定型文自動生成、③の機器台数入力、後述の「よく使う文」がいずれもこの目的のための機能）。

### 3.5 進行案内（いま何をすればよいか）

- ①〜③の各カード（`.step-card` / `#step1`〜`#step3`）の見出しに**進捗バッジ**（`#badge1`〜`#badge3`）を出す。
  ②は「入力できた件数 / 稼働件数」を表示し、すべて埋まると緑（`ok`）になる。
- **いま取り組むカード**（未完のいちばん手前）に `now` クラスを付け、枠を強調する。
- その項目が終わったら、カード下部に**次へ進む案内**（`.step-next` / `#next1`〜`#next2`）を出す。
  「次へ」ボタン（`goStep(n)`）で次のカードへスクロールし、最初の入力欄にフォーカスする。
- 入力・選択・登録のたびに `updateWizardNav()` を呼んで、表示を最新に保つ。

### 3.6 クリア（最初からやり直す）

- ①のカード内に「クリア（最初からやり直す）」（`#btn-cal-clear` → `clearWizardAll()`）を置く。
  ①業態を先頭の項目へ・稼働件数を1件へ戻し、`renderStoreRows()` で②の行数を1件に揃えたうえで
  `resetStoreRows()` により日付・時刻・店舗名・住所を空に戻す。
- **③の登録リスト（`entries`）もこのボタンで一緒に消す。** まだGoogleカレンダーへ登録していない
  ③の一覧も「最初からやり直す」の対象に含める。**`entries.length` が1件以上あるときだけ
  `confirm()` で確認ダイアログを出す**（0件なら確認なしでそのままクリア）。
  ③にある既存の「全て削除」（`clearAllEntries()`）は変更せずそのまま残す
  （③だけをピンポイントで消したい場合に使える）。
- `clearDayAll()`（作業当日タブ）と異なり `clearDraft()` は呼ばない。呼ぶと下書き全体
  （当日タブ側の入力途中の内容も含む）が消えてしまうため、`saveDraftSoon()` によるカレンダー部分のみの
  上書きに留める。

### 4.1 予定の読み込み

**「業態を選んで店舗名を入れるだけ」で連絡文が作れることが、この画面の主役である**（4.1.1）。
Googleカレンダーの説明文の貼り付け（`#day-paste` → `loadDayFromPaste()`）と、
「このアプリの登録リストから探す」（`loadDayFromList()`）は、同じカード内の折りたたみ（`#gy-paste`）に
まとめた**補助動線**とする。定型文とは違う内容で連絡したいときに使う。
主動線が埋もれるような画面変更をしないこと。

**Googleカレンダーからの直接読み込みは廃止した。** 利用者ごとにカレンダーが異なり、
全員で1つの設定を共有するこのアプリの方針と噛み合わないため。設定項目だけは5.4節に残してある。

- 日付は上部の日付入力で切り替えられる（既定は当日）。
- 候補が複数ある場合は一覧から選択。1件のみなら自動選択。
- タブを開いたときは登録リストの候補を作り直すが、**表示中の連絡文は上書きしない**（カレンダー由来の候補も保持）。

### 4.1.1 業態と店舗名から連絡文を作る（主動線）

- 「🛠️ 作業当日」タブの先頭で、**業態（`#day-gyotai`）と店舗名（`#day-tenpo`）だけ**を指定して
  「この内容で連絡文を作る」（`buildDayFromGyotai()`）を押すと、その業態の定型文から
  ①入店連絡／②中間報告／③退店連絡を生成する。Googleカレンダーを開く必要はない。
- 時刻は**開始・終了を直接指定する**（`#day-start` / `#day-end`）。業態を選ぶとその業態の1つめの時間帯の時刻が
  初期値として入り（`applyGyotaiTimesToDay()`）、そこから自由に変えられる。終了が開始より前なら自動で揃える。
  どの定型文を使うかは開始時刻から決める（`slotNearestTime()`）。時間帯（午前/午後）のラジオは廃止した。
- 「クリア（最初からやり直す）」（`clearDayAll()`）で、店舗名・連絡文・機器台数・入店連絡と中間報告の選択・
  貼り付け欄・下書きをすべて消して初期状態に戻す。
- **業態ごとに「注意事項」（`g.notes[]`、`{id, place, text}`の配列）を複数登録できる。**
  `place`は①入店連絡／②中間報告／③退店連絡のいずれかで、業態を選ぶと③カード内の該当する連絡文欄
  （`#msg-in`/`#msg-mid`/`#msg-out`）の直前にそのままの`place`の注意事項だけを表示する
  （`#day-gyotai-notes-in`/`-mid`/`-out` / `updateDayGyotaiNotes()`）。報告用の写真の撮り方・撮影項目などを
  想定した自由記述で、同じ欄に複数あれば空行区切りで並べる。**該当する注意事項が無い欄には表示しない**
  （要素ごと`hidden`にする）。業態を切り替えるたびに内容を更新する。各行の前後の空白は表示前に取り除く
  （`trimLines()`）。
- **業態ごとに「手順書・資料」（画像・PDF）を複数登録でき、業態を選んだ時点で内容が決まる**
  （`g.manuals[]` = `{id, name, type, url, size}`の配列 / `#day-gyotai-manuals` / `updateDayGyotaiManuals()`）。
  **表示位置は「この内容で連絡文を作る」ボタンの下・「クリア」ボタンの上**（利用者の指定）。
  画像はサムネイル、PDFは「PDF」の小さなバッジで表示する。タップ（クリック）したときのリンク先は
  種類ごとに違う（`manualHref(m)`）: 画像はそのまま直接開き、**PDFは`manual-view.php`を経由して
  ダウンロード形式（`Content-Disposition: attachment`）で渡す**ことで、端末の既定のPDFアプリ
  （Acrobat Readerなど）で開けるようにする（ホーム画面から起動したPWA内ではPDFがまともに開けない
  という問題への対策。詳しくは5.2節参照）。連絡文をまだ作っていなくても中身は決まる（業態を選んだ時点で）。
  該当する資料が無い業態では非表示。詳しい保存の仕組み（アップロード先のサーバー、権限、対応形式）は 5.2 を参照。
- 店舗名は `applySuffix()` で語尾（既定は「店」）を補ってから使う。生成した内容は `setDayCtx()` に渡すため、
  「今日の作業」の表示・Chatボタンの業態＋店舗照合・よく使う文の差し込み文字も従来どおり働く。
- ③退店連絡の機器台数（MPR/MST/HT/BC/BP、1〜10のプルダウン）は従来どおりで、選んだ機器だけが追記される。
- Googleカレンダーの説明文の貼り付けは、同じカード内の折りたたみ（`#gy-paste`）に置いた**補助動線**とする。

### 4.2 説明文の振り分けロジック `splitReport()`

1. HTML混じりの説明文はプレーンテキストへ変換（`<br>`→改行、タグ除去、実体参照の復号）。
2. 空行（`\n\s*\n`）でブロックに分割し、空ブロックを除去。
3. 「中間報告の目印」を含む最初のブロックを `iMid`、その後ろで「退店連絡の目印」を含む最初のブロックを `iOut` とする。
   `iOut` が見つからない場合は `退店` でも探す。
4. 振り分け:
   - **入店連絡** = 先頭 〜 `iMid`（または `iOut`）の直前
   - **中間報告** = `iMid` のブロック
   - **退店連絡** = `iOut` 以降すべて（入店/退店時刻、機器カウントを含む）
5. どちらの目印も無い場合は全文を入店連絡に入れる。

目印は設定で変更可能（既定 `中間報告` / `退店報告`）。

### 4.3 業態・店舗名・時刻の推測 `detectFromText()`

- 登録済みの業態名を本文から検索し、見つかった行の業態名の直後のトークンを店舗名とみなす（数字始まりは除外）。
- `入店 HH:MM` / `退店 HH:MM` を正規表現で拾う。
- 登録リスト由来・カレンダー由来の場合は、そちらの値を優先する。

### 4.4 よく使う文（定型フレーズ）

- 連絡文カードの下に、控えめな帯（`.phrase-bar`）として小さなチップを並べる。押すとその文をコピーする。
- 予定を読み込んでいなくても使える（`dayCtx` に依存しない）。
- 差し込み文字に対応。`dayCtx` があれば `{業態}` `{店舗名}` `{日付}` `{開始}` `{終了}` を置換する。
- チップの表示は1行目のみ・26文字で省略。コピーされるのは全文。
- 初期値: お疲れ様です／ご確認よろしくお願いします／現地に到着しました／作業を開始します／作業完了しました／ありがとうございました
- 設定画面「よく使う文（定型フレーズ）」で追加・修正・削除・並び替え（↑↓）ができる。0件にすると帯ごと非表示。
- 設定画面の編集欄は**1行の `<input>`** とし、↑↓・削除ボタンと横並びにする（`.ph-row`）。
  縦に長くならないようにするための指定なので、複数行の `<textarea>` に戻さないこと。

### 4.4.1 入力内容の一時保存（下書き）

- スマートフォンでは画面の更新やアプリの切り替えだけで入力が消えるため、**入力途中の内容**を
  `localStorage`（キー `oes-calendar-draft-v1`）に400msの遅延つきで保存する（`saveDraftSoon()`）。
- 保存対象: 作業当日タブ（業態・店舗名・日付・開始/終了時刻・生成した連絡文・機器台数・入店連絡の選択・貼り付け欄）と、
  カレンダータブ①②③の入力（業態・稼働件数・各行の日付/開始/終了/店舗名/住所）。
- **登録リスト（`entries`）は従来どおり保存しない。** 共有設定でもなく、その端末だけの一時的な控えである。
- 復元（`restoreDraft()`）は**共有設定の読み込みが完了してから**行う。先に戻すと、
  設定に合わせて行を作り直したときに消えてしまうため。復元したときはトーストで知らせる。
- 保存から**24時間**経った下書きは使わずに削除する（前日の入力が残らないように）。

### 4.4.2 ①入店連絡・②中間報告に足す文（選択式）

- `settings.entryNotes` / `settings.midNotes`（どちらも `[{id, text}]`）の文を、それぞれ入店連絡・中間報告
  欄の上にチェックボックス（`#entry-note-row` / `#mid-note-row`）で並べる。**チェックした文だけ**がその本文の
  1行目（見出し）の直後に、設定の並び順で差し込まれる（`rebuildEntryNoteBlock()` / `rebuildMidNoteBlock()`。
  機器台数と同じ「選んだものだけ入れる」方式）。
- `entryNotes` 初期値: POSレジ清算済み／POSレジ清算 今から開始をお願いいたしました
- `midNotes` 初期値: 高所の為、電源ケーブル流用させて頂きます／スパイラル多用の為、電源ケーブル流用させて頂きます／
  店舗名多忙の為、入替作業は状況見て実施します。（利用者からの指定で中間報告側に配置）
- これらは以前 `TPL_SUKIYA`（すき家の定型文）に直接書かれていたが、選択式へ移したため定型文からは削除した。
  読み込み時に定型文由来の同じ行があれば取り除く（`stripEntryNoteLines()` / `stripMidNoteLines()`）。
- 設定画面「入店連絡に足す文」「中間報告に足す文」（別カード）で、それぞれ追加・編集・並び替え・削除ができる
  （管理者のみ）。

### 4.4.3 ③退店連絡の特記事項

- ③退店連絡の入力欄の下に「特記事項（任意）」（`#msg-remark`）を置く。
  **③の「コピー」ボタンは、この特記事項欄よりさらに下＝③の一番最後に置く**（①②のコピーボタンは
  各テキストエリアの直下だが、③だけは特記事項まで入力してからまとめてコピーする流れに合わせている）。
- `#msg-remark` は他のtextareaの既定の高さ（`min-height:130px`）だと縦に長すぎるため、
  個別に `min-height:68px` を指定して**2〜3行程度の高さ**にしている（`resize:vertical`なので
  手動で広げることはできる）。
- **入力された場合だけ**、退店連絡の本文のいちばん最後に **`【特記事項】` の見出し付き**で、
  空行をはさんで追記する。空欄・空白だけのときは見出しごと何も足さない
  （機器台数と同じ「入力したものだけ入れる」方針）。
- 本文は `rebuildOutBlock()` が毎回 **「本文 → 機器台数 → 【特記事項】＋入力内容」** の順に組み立て直す。
  直前に入れた見出し込みのブロックを `appliedRemark` に控えておき、それを取り除いてから足し直すので、
  書き換えても二重にならない。本文を手で書き換えていた場合は、消さずにそのまま残す。
- 下書き（4.4.1）にも保存し、画面を更新しても入力が残る。
  「クリア」「別の作業の読み込み」では消える（次の店舗に持ち越さない）。

### 4.5 表示とコピー

- 「今日の作業」に 日付／業態 店舗名（22px）／時刻／住所（Googleマップリンク）を表示。
- 連絡文は3つのテキストエリアで編集可能。**「コピー」ボタンは、見出しの隣ではなく
  各テキストエリアの直下**に置く（押下後1.6秒だけ緑＋「コピーしました」）。見出しの隣に置くと、
  隣の欄のボタンと近くて誤タップしやすいという利用者の指摘により、各欄の最後の要素として配置している
  （③退店連絡だけは「特記事項」欄の下＝4.4.3参照）。
  **①②③個別の「Chat」ボタンは廃止した**（理由は4.5-2参照）。
- コピーは `navigator.clipboard.writeText`（セキュアコンテキスト時）→ 失敗時は `textarea` + `execCommand('copy')` にフォールバック。
- 「定型文から作り直す」で読み込んだ内容から再分割。
- Google Chatを開く入り口は、「今日の作業」カードの「Google Chat を開く」（`#btn-open-chat`）と、
  画面下部「よく使う文」欄の直前に置いたもう1つのボタンの、**合計2箇所**（どちらも同じ
  `openStoreChat()` を呼ぶ。4.5-2参照）。

#### 4.5-1 機器の台数（③退店連絡のみ・入力した機器だけ反映）

- ③退店連絡のテキストエリア直上に、`MPR` `MST` `HT` `BC` `BP` 5種類の**プルダウン**（`<select>`、値は
  空欄または1〜10）を並べる（`#equip-row`）。単位はBPのみ「個」、他は「台」（`EQUIPMENT_UNITS`）。
  台数は多くても現場のプリンター・端末の台数を大きく超えないため、自由入力の数値欄ではなく
  1〜10のプルダウンにして誤入力（文字混入・桁間違い）を防ぐ。
- **説明文に含まれる機器台数の行（`MPR   台` のような空欄プレースホルダを含む）は、予定を読み込んだ時点で
  いったんすべて取り除く**（`stripEquipmentLines()`）。読み込み直後・何も選んでいない状態では、
  ③の本文に機器の行は一切表示されない。
- 数値を選んだ機器だけ、`コード + '   ' + 数値 + 単位` の形式で③の末尾にまとめて追記する
  （`rebuildEquipmentBlock()`）。追記順は選んだ順ではなく常に `MPR → MST → HT → BC → BP` の固定順。
  空欄に戻すとその行だけ消える。
- ③のテキストエリアを直接手で編集しても、プルダウンの値を変えるたびに機器の行だけを安全に置き換える
  （テキスト中の他の内容には触れない。ただし手動で `MPR` 等から始まる行を書いた場合はその行も対象になる）。
- 「登録リストから探す」等で別の作業を選び直す、または新しく貼り付け直すと、5つのプルダウンは空欄にリセットされる
  （`dayCounts` は `setDayCtx()` のたびに初期化）。「定型文から作り直す」では、選択済みの値は保持したまま
  本文だけ読み込み内容から作り直す。

#### 4.5-2 Google Chatを開く（検索語のクリップボードコピー方式）

- **目的:** 作業のたびにGoogle Chatの一覧から該当の業態・店舗のルーム／DMを探す手間を減らす。
- **旧仕様（`settings.storeChats`による業態・店舗ごとのURL事前登録）は廃止した**（利用者の指示。
  データ構造ごと削除済み。復活させないこと）。廃止理由:
  1. 登録の手間がかかる。
  2. 登録したURLがルーム/一覧のトップだと、Chat内で他のスレッドへ移動したあとにもう一度
     ボタンを押すと元のURLへ戻ってしまう不具合が繰り返し報告された。
  3. **タブ側の状態（開き直すべきか否か）をこちらのJSから正しく検知する方法が無い。**
     3つの実装を試し、いずれも実機か自動テストで問題が確認された:
     - `chatWin.focus()` だけを呼んで開き直さない方式 → Google ChatのCOOP
       （Cross-Origin-Opener-Policy: same-origin）により、一度別オリジンへ移動した参照は
       ブラウジングコンテキストグループごと切り離され、`.focus()` が実際には効かない
       「無反応」になることが実機で確認された。
     - `window.open('', name)` で空URL取得のみ行う方式 → 一部のモバイル環境のポップアップ
       ブロッカーに無反応にされることが実機で確認された。
     - `document.hasFocus()` でフォーカス成否を自動判定し、失敗時だけ開き直す方式 →
       実際に正常動作した場合でも `hasFocus()` がtrueのままになる環境があり、誤って
       開き直してしまうことが自動テストで確認され、採用を見送った。
  4. **Google Chatの検索欄はURLと連動しない。** 実際に検索してもブラウザのアドレスバーの
     URLは変化しない（利用者に実機で確認済み）。そのため「検索語を含むURLを開く」という
     方法自体が存在しない。
- 上記の理由から、`openStoreChat()`はポップアップ側の状態に一切関与せず、次の1つだけを行う:
  1. `window.open('https://chat.google.com/', 'oes-store-chat')` で、一般のGoogle Chatを
     名前つきウィンドウとして開く（同じ名前のウィンドウがすでに開いていればブラウザ側の

## 4-2. 画面4: コマンド一覧（保守機能のシミュレーター）

実機（SEIKO SA-2610 マルチステーション）の操作パネルを画面上で再現し、「この保守機能はどのボタンを

カレンダー → 作業当日 → **コマンド一覧** → 設定。

### 4-2.1 画面の構成

**1枚のカード**（`#pane-cmd .card`。タイトルは「**Monstera/Relier シミュレーター**」）に、
シミュレーター本体と手順ガイドをすべて収める。**「①」「②」のような番号付きの区切りは置かない**
（以前は「①機器の画面（シミュレーター）」「②操作を選んで手順を見る」の2枚のカードに分けていたが、
利用者の指示で1枚に統合した。分割方式に戻さないこと）。カード内の並び順は次のとおり：

1. 待機画面の切り替え（`#sim-idle-view`）: 何も操作していないときに出す画面を、練習用にその場で
   切り替えられるプルダウン。選択状態は`curIdleId`という一時変数で持ち、共有設定には入らない
2. シミュレーター本体（`.sim-panel`）
   - **キーパッドとは別枠の「電源スイッチ」**（`.sim-pwrsw` / `#sw-rocker`）。実機の側面などに
     ある電源スイッチのイメージで、**上＝ON・下＝OFF**（`SIM_SWITCH_KEYS`の`PWRSW_ON`/`PWRSW_OFF`）。
     「何かのボタンを押しながら電源を入れる」操作を再現するため、**キーパッド本体のキーと完全に同じ
     press/hold/同時押しの仕組み**（`simDownKey()`/`simUpKey()`/`checkStayDownMatch()`）に乗っている。
     手順編集のキー選択（プルダウン）にも「電源スイッチ（枠外）」というoptgroupで登場し、
     通常のキーと同じように`keys`配列へ入れて他のキーとの同時押し・押しままの手順に使える。
     押した瞬間に見た目（`.sw-active`）と電源LED（`#led-power`）の点灯状態が切り替わる
     （`updatePwrSwitchVisual()`）。画面の枠外の操作なのでアプリの2色ルールの対象外（実機の再現）。
     **画面の幅にかかわらず、常にシミュレーター画面の左に横並びにする**（`.sim-with-switch`。
     以前はスマホ幅では画面の上に縦積みにしていたが、それだと余白ができて「変な位置」に見える
     と利用者から指摘され、常に横並びに変更した。狭い画面でも固定幅211pxの表示部と衝突して
     横スクロールが出ないよう、`.sim-top`・`.sim-panel`・`.sim-with-switch`・`.sw-rocker`の
     余白は最小限にしてある。アプリの標準テスト幅である390pxでは、`document.body.scrollWidth`が
     増えないことに加えて、**`.sim-panel`が`.card`の枠内に、`.sim-screen`が`.sim-top`の
     内側に収まっている**ことも確認済み（後者だけを見落とすと、ページ全体は横スクロールしない
     まま入れ子の内側だけで静かにあふれる不具合が起こる。5.x節の実例を参照）。
     それより極端に狭い画面（375px以下）は対象外）。`.sim-panel`には**`min-width:0`を付けない**
     （既定の`min-width:auto`のままにして、幅が足りないときは中で静かに縮んで内容がベゼルの外へ
     あふれるのではなく、`.sim-panel`自身が正直に必要な幅を取る＝入らなければ
     `document.body.scrollWidth`で検知できる状態を保つ）。
   - LEDランプ（電源・オンライン・通信中・エラー・コントローラ）と表示部（`.sim-screen`）を、
     **1つの黒いベゼル**（`.sim-top`）にまとめている（実機の写真を参考にした見た目）。
     - LEDは黒地に緑の文字・アイコン（`.sim-led`、点灯時は明るい緑・グロー付き）。
       電源LEDは電源スイッチの状態と連動、他は飾りで点灯状態は固定。
     - 表示部（`.sim-screen`）: 黒いベゼルの地色の上に、白文字のブランド名`SEIKO`とモデル名
       `SA-2610`（実際の表示部の外）、そして**うす緑がかった地色に黒文字**のLCD
       （`.sim-lcd-box`内の`#sim-l1` / `#sim-l2`）がある（実機写真を参考にした配色。
       以前は白地に黒文字だった）。初期表示は管理者が設定した待機画面から選ばれている1つ
       （`settings.idleScreens`、後述）。
       **表示部の大きさは内容にかかわらず常に固定**（幅211px・高さ64px）で、折り返しはせず、
       長い文字は`fitLcdLine()`が文字サイズだけを縮めて枠内に収める（17px〜8pxの範囲）。
       **幅・高さ・文字サイズ（`LCD_FONT_MAX`）の変遷**：①270px・54px・15px→②利用者の指定
       「右側の余白が気になるので少し縮めて、縦にはもう少し広げられる。縦を広げたら文字も
       少し大きくする」で270→250px・54→64px・15→17pxへ調整→③電源スイッチを常に横並びに
       した際にスマホの実機で表示部が黒いベゼルの外へあふれる不具合が見つかり、余裕を持って
       収まるよう250→224pxへさらに縮めた→④利用者の指定「ディスプレイの右側の黒の余白が
       狭すぎる。黒の余白増やしてほしい」で、`.sim-top`の右パディングを3→16pxに広げ、
       その分`.sim-screen`を224→211pxへ縮めて表示部の右に黒いベゼルの余白を確保した
       （狭くなった分、長い文字列は`fitLcdLine()`による自動縮小がより早く働くようになるが、
       これは想定内の動作。「文字サイズを小さくしても、画面のはみ出しはNG」という利用者の
       方針どおり、あふれないことを優先する）。
   - キーパッド（`#sim-keys`）: 実機どおりの7列×3行
     （`F △ シフト A1 B2 C3 電源` / `◁ メニュー ▷ D4 E5 F6 0` / `（黒い飾り） ▽ 実行 7 8 9 クリア`）。
     F・△・シフト・◁・▷・▽・メニュー・電源・クリアは画面と同じ黒、実行だけは茶色、それ以外（数字）は
     既定の明るい色（実機の見た目に合わせるための例外で、アプリ全体の2色ルールとは無関係）
   - 画面が広い（760px以上）ときは、実機と同じように画面の右側にキーパッドを並べる
     （このとき画面とキーの間に余計な余白ができないよう、画面側の幅は内容ぶんだけに抑える）
3. **シミュレーターの直後**（`#sim-msg`/`#sim-note`/長押し等の案内文を挟まず）に「調べたい操作」の
   プルダウン（`#cmd-select`）を配置する（利用者の指示：「画面シミュレーターのすぐ下に調べたい操作の
   プルダウンを配置して」「ディスプレイの下には、調べたい操作を配置して」。以前は`#sim-msg`/`#sim-note`/
   長押し等の案内文（`.hint`）がシミュレーターと`#cmd-select`の間に挟まっていたが、それらは
   後述の「進行状況」側へ移した）。
4. **この操作が役に立つ場面**（`#cmd-usage`。`commands[i].usage`、任意。登録されていれば💡付きの
   アンバー色の帯で表示、無ければ非表示）。**左に太いアクセント線、13.5pxの太字、
   「この操作の使いどころ：」という見出しラベル付き**で、それ以外の説明（`.hint`）より強調している
   （利用者の指定「入力した情報をもう少し強調して表示したい」で、以前の12px・アクセント線無しから
   強調度を上げた）、説明（`#cmd-note`）。
5. 手順ガイド本体（`.cmd-guide-body`）。画面が広いときは左右2列、狭いときは縦に並ぶ。
   **左＝再生系の操作と簡易手順、右＝進行状況（手順チップ＋案内文）**という組み合わせにする
   （利用者の指定：「調べたい操作を画面の下に配置、秒数の下に簡易手順を配置、今の簡易手順があるところに、
   進行状況を表示してほしい。進行状況は改行されてもよいので」→「進行状況と添付画像の文章表示して」で、
   `#sim-msg`/`#sim-note`/長押し等の案内文（`.hint`）を「進行状況」側にまとめた）。
   - 左（`.cmd-guide-left`）: 「順番に再生」「1つ進む」「最初から」、「順番に再生」次に進むまでの秒数
     （`#cmd-play-speed`）、**その下に**「簡易手順」＝手順を上から順番に読める文章のリスト
     （`#cmd-textlist` / `renderCmdTextList()`）。シミュレーターの動き（実質的な「動画」）だけでは
     分かりにくいという声を受けて追加した。各行に手順の内容（`simStepLabel()`と同じ表現）、
     画面に出る文字（あれば）、結果コメント（あれば）を表示し、いま案内中の手順を
     `renderCmdSteps()`と同時にハイライトする（`.on`/`.done`）。
     **文字色は`.cmd-textlist`で`var(--ink)`・太字**にして、はっきり読めるようにしている
     （淡いグレーで読みにくいという指摘を受けて濃くした。画面部分の`.tl-scr`だけは少し控えめな濃さ`#3A3D40`）
   - 右（`.cmd-guide-right`）: **「進行状況」**の見出しのもとに、上から順に
     ①手順チップ（`#cmd-steps`。9×2 → 8 → 実行 → 完了、のようにいま案内中のステップを
     色分けハイライトして示す一覧。右側の狭い列に収まるよう`flex-wrap:wrap`で自然に改行される。
     利用者の指定「進行状況は改行されてもよい」のとおり）、
     ②案内メッセージ（`#sim-msg`。「◯◯を押してください」「長押し中…」「✅ 完了」など）、
     ③画面は変わらないが実際には何か起こる操作の説明（`#sim-note`。空なら非表示）、
     ④長押し・同時押しに対応している旨の固定の案内文（`.hint`）を並べる。
     以前はこの3つ（`#sim-msg`/`#sim-note`/`.hint`）はシミュレーターの直下、`#cmd-select`より
     前にあったが、利用者の指定「進行状況と添付画像の文章表示して」で「進行状況」列へ移した。

### 4-2.2 データ構造（共有設定に入る）

```js
settings.idleScreens = [                       // 待機中（何も操作していない）画面。複数登録できる
  { id, name:'二重化（メイン）', l1:'二重化　（メイン）', l2:'[01]　{time}' },
  { id, name:'メイン単独',       l1:'メイン　単独',       l2:'[01]　{time}' },
  { id, name:'サブ単独',         l1:'サブ　単独',         l2:'[02]　{time}' },
  { id, name:'電源オフ（表示なし）', l1:'', l2:'' }
];
settings.commands = [
  { id, name, note, usage:'',                   // この操作が役に立つ場面（任意、②カードに💡表示）
    idleScreen:'',                               // idleScreensのid。空なら「今選んでいる画面のまま」
    steps: [
      { id, keys:['9'], hold:false, stayDown:false, repeat:1, l1:'', l2:'', memo:'' }
    ] }
]
```

- `idleScreens`の`name`はプルダウンに出る名前、`l1`/`l2`はLCDに出る1〜2行目（`{time}`だけ現在時刻に
  置換。両方空にすると「電源オフ」のような何も表示されない画面になる）。最低1件は残す（削除は不可）。
  旧バージョン（`simIdleL1`/`simIdleL2`という単一の待機画面）の設定は自動で1件だけの配列に移行される。
- `commands[i].usage` は**この操作がどんな場面で役に立つかの説明**（任意）。②カードの`#cmd-usage`に
  💡付きで表示する。手順そのものではなく「なぜこの操作をするのか」を書く欄。
- `commands[i].idleScreen` は**このコマンドを選んだ瞬間に切り替える待機画面**（任意）。実機は電源の
  状態や二重化の構成によって前提が違うため、コマンドごとに「始める前の状態」を指定できる。
- `keys` は `SIM_KEYS` または `SIM_SWITCH_KEYS`（電源スイッチ）のidの配列。**2つ入っていれば同時押し**
  （例: `['LEFT','RIGHT']`、`['PWRSW_ON','7']`のように電源スイッチと通常キーの組み合わせも可）。
- `hold:true` なら**長押し**（押して離すまで600ms以上）。`stayDown:true` なら**押しまま**
  （離すのを待たずに、押した時点で次のステップへ進む。Fを押したまま次のキーを押す、のような操作向け）。
  `repeat`（1〜20）は**同じボタンを連続で何回か押す**手順。`hold`・`stayDown`・`repeat>1`は互いに排他
  （どれか1つを設定すると残り2つは既定値に戻る）。
- `l1` / `l2` はそのボタンを押し終えたときにLCDの1行目・2行目へ出る文字（上下行を別々に持つ。
  空ならその行の表示を変えない。旧フィールド`display`は`l1`として後方互換で読み込む）。
- `memo` は**画面は変わらないが実際には何か起こる操作**（明細票の印刷など）の説明。LCDには出さず、
  `#sim-note` にだけ表示される。
- **`SIM_KEYS` / `SIM_SWITCH_KEYS` のidは保存データなので、あとから変えないこと**（登録済みの手順が壊れる）。
  `simKeyDef(id)`はどちらの配列も見るので、キーの定義取得やラベル表示は電源スイッチも通常キーも同じ
  関数（`simKeyLabel()`/`simStepLabel()`）で扱える。
- 初期サンプル（`defaultCommands()`）: 保守機能モードに入る（◁＋▷の同時長押し）/
  インストール情報を表示する（9を2回→8→実行）/ 電源を切る（電源長押し→電源）/
  システムIDを確認する（メニュー）/ 取引明細を印刷する（結果コメントのみ・画面は変わらない）。
- コマンドは**複製できる**（`duplicateCommand()`）。手順が途中まで同じものが多いため、既存のコマンドを
  複製してから一部だけ書き換えられる。複製は元の直後に挿入され、名前に「（コピー）」が付く。

### 4-2.3 2つの使い方（どちらも同じ手順データを使う）

1. **手順ガイド**: プルダウンで操作を選ぶと、手順がチップで出る（`9×2 → 8 → 実行 → 完了`）。
   連続押しの手順は「今何回目/全部で何回」を、長押しの手順は「長押し」を色分けして示す。
   ハイライトは常に光っているように動く（通常・長押し・押しままは呼吸するようなグロー、
   連続で何回か押す手順だけははっきり色が切り替わる点滅）。
   - 「順番に再生」（`cmdPlay()`）: キーを順にハイライトしながら自動で進む。長押しのステップは長めに止まる
     （既定は通常1200ms・連続押し1回ぶん650ms・押しまま800ms・長押し2200ms）。
     **`#cmd-play-speed`（「次に進むまでの秒数」）で0.8〜3秒の間で変更できる**（`setCmdPlaySpeed(v)`。
     通常の間隔をそのまま秒数として使い、長押し・押しまま・連続押しの間隔は既定の1.2秒との比率で
     一緒に伸び縮みする＝`cmdPlayIntervals()`。共有設定には入れない見る人ごとの好みで、
     `cmdPlay()`を開始した時点の値がその回の再生に使われる）。
   - 「1つ進む」（`cmdNext()`）: 1ステップずつ進める。
   - **実機のキーを自分で押しても進む**（`cmdTryAdvance()` が次のステップと一致するか見る。
     連続押しの手順は規定の回数に達するまで同じステップにとどまる）。
   - **「押しまま」のステップだけは、離すのを待たずに押した時点で次へ進む**
     （`simDownKey()` 内の `checkStayDownMatch()`。あとで実際にキーを離しても二重には進まない）。
   - 進むたびに、直前のステップの `l1`/`l2`（あれば）をLCDに、`memo`（あれば）を`#sim-note`に反映する
     （`cmdGo()`）。
2. **自由に押す**: プルダウンを使わずキーを押すと、押した履歴（`simInput`、最大12件）と、登録済みコマンドを
   「1回押し単位」に展開したもの（`expandPhysicalSteps()`。連続押しは実際の回数ぶんに開く）とを
   前方一致で照合する（`simMatchProgress()`）。
   - **途中まで一致**していれば、そこまでのステップの `l1`/`l2` をLCDに出し、「あと◯回」と案内する。
   - **最後まで一致**したら、そのコマンドの画面（あれば）を出してトーストで知らせる（`simShowCommand()`）。
     **画面に出す文字が1つも登録されていない操作は、完了してもLCDを変えない**（実機と同じ挙動。
     その代わり `memo`（あれば）を `#sim-note` に出す）。
   - 完了しているコマンドを、途中までしか一致していないコマンドより優先する。
   - 「クリア」キーは履歴を消して、いま選んでいる待機画面（`curIdleScreen()`）に戻す。
   - この前方一致の途中表示が無いと、「電源長押し→確認表示→もう一度押して終了」のような段階的な操作で
     長押ししても何も起きないように見えるため、**この動作は消さないこと**。

### 4-2.4 長押し・同時押しの判定

- `pointerdown` で押されたキーを覚え、**押されているキーが全部離れた時点**で1回の操作として確定する
  （`simDownKey()` / `simUpKey()`）。
- 押していた時間が `SIM_HOLD_MS`（600ms）以上なら**長押し**。600ms経過した時点でキーが点滅し、
  案内に「長押し中…」と出る。
- その1回の操作の間に押されていたキーをまとめて**同時押し**として扱う。
- マウスはポインタが1つしかないため同時押しできない。実機（スマホ）か、自動テストで `PointerEvent` を
  2つ送って確認する。

### 4-2.5 設定画面での編集（管理者のみ）

設定タブの「コマンド一覧（保守機能の操作手順）」カード（`#cmd-list` / `renderCommandList()`）で編集する。
カードの先頭には待機画面のリスト（`#idle-screen-list` / `renderIdleScreenList()`）もある。

- 待機画面は単純なリスト（`.is-row`）で編集する: 名前・1行目・2行目・並び替え（↑↓）・削除。
  「＋ 待機画面を追加」で増やせる。**最低1件は残す**（最後の1件は削除できない）。
- コマンド一覧は**折りたたみ式**（`.gy-item`）。見出しは「コマンド1」＋インライン編集できる操作名＋
  **この操作を選んだときの待機画面（プルダウン、任意。空なら「今の画面のまま」）**を表示し、
  見出しをクリックすると説明・手順・並び替え（↑↓）・複製・削除が開く（開閉状態は`cmdOpenSet`で保持）。
  **待機画面の選択欄は見出しに直接あるので、コマンドを開かなくても選べる**。
  「＋ コマンドを追加」ボタンは**コマンド一覧のすぐ上**（待機画面のリストより下）にあり、押すと自動的に
  開いた状態のコマンドが追加される。「複製」を押すと、同じ手順を持つコピーがすぐ下に挿入され、
  名前に「（コピー）」が付く（多くの手順が途中まで同じ場合に使う）。
- コマンドごとの項目: 説明（任意、開いた詳細欄）／**この操作が役に立つ場面**（任意、`c.usage`。
  ②カードの`#cmd-usage`にそのまま反映される）。
- 手順（1行＝1回の操作）: 押すボタン（プルダウン）/ 同時に押すボタン（プルダウン、既定は「同時押しなし」）/
  長押し（チェック）/ **押しまま**（チェック。離すのを待たずに次の手順へ進む）/
  連続回数（1〜20。長押し・押しままとは排他）/ 画面1行目・2行目（任意、別々の欄）/
  結果コメント（任意、画面が変わらない操作の説明）/ 並び替え（↑↓）/ **この手順のすぐ後に1つ差し込む（＋）**/
  削除。**押し忘れたボタンをあとから途中に追加できる**（各行の「＋」でその手順の直後に、
  一覧の先頭にある「＋ 先頭に追加」で最初に挿入する。挿入した手順は既定値（`9`）で入るので、
  そのあと押すボタンやオプションを設定し直す）。並び替え（↑↓）と組み合わせれば、順番の入れ替えと
  途中への追加のどちらにも対応できる。
- CSVで一括登録・書き出しができる（「CSVで書き出す」「CSVから読み込む」）。列は
  「コマンド名,説明,役立つ場面,待機画面,ボタン1,ボタン2（同時押し）,長押し,押しまま,連続回数,
  画面1行目,画面2行目,結果コメント」で、同じ「コマンド名」の行が連続していると1つの操作としてまとめる。
  「待機画面」列は名前で指定し、一致するものが無ければ未設定（今選んでいる画面のまま）になる。
  「ボタン1」「ボタン2」には電源スイッチのid（`PWRSW_ON`/`PWRSW_OFF`）もそのまま書ける。
  書き出しはBOM付き（Excel文字化け対策）。
  **読み込むと`settings.commands`は丸ごと置き換わる**（確認ダイアログを経て）。待機画面一覧自体はCSVの対象外。
- 変更は共有設定（`settings.json`）に入るので、管理者が登録すれば全員の端末に反映される。

## 4-3. 画面5: レポートの見方（インストールレポートのナビゲーション）

実機が印字する「MONSTERA インストールレポート」の読み方を、実物と同じ桁で並べた印字例の上で
たどれる画面（`#pane-rep`）。利用者から渡されたExcel「MONSTERAインストールレポートデータの見方」
（`98レポート`シート）の内容をそのままデータ化したもの。タブの並びは
カレンダー → 作業当日 → コマンド一覧 → **レポートの見方** → 設定。

### 4-3.1 データ構造

`REPORT_GUIDE` としてコードに固定で持つ（**共有設定`settings.json`には入れない**。実機レポートの
仕様そのもので、担当者ごとに変える性質のものではないため）。

```js
REPORT_GUIDE = {
  title, lead,
  sections: [{
    id, name, note,                    // 章（インストール情報／システム情報／ECT／MST／MPR／MD／HT）
    fields: [{k:'A', n:'機器名称'}],    // 記号と中身（記号のある章だけ）
    sample: {title, rows:[['A','ECT01']]},  // 元Excelの「左記例」
    notes: ['…'],                      // 章の注意書き
    lines: [{                          // 印字例の1行
      desc,                            // ← 行にマウスを乗せたときの説明
      code,                            // 任意。ini の記載イメージなど
      head, gap,                       // 見出し行／空行
      toks: [{p, t, k, d, pick, code}] // p=桁位置, t=文字, k=記号, d=値だけの詳しい説明
    }]
  }]
}
```

### 4-3.2 画面と操作

- **レポートは章ごとに分けず、実機の印字どおり1本の縦長でそのまま出す**（利用者の指定：
  「項目ごとに分けるのではなく、レポートの一覧をそのまま表示して」「レポートは縦にそのまま表示」）。
  最初は章を切り替えるチップ方式だったが、通しで出す形に作り直した。**章切り替え方式に戻さないこと。**
  全章の行は`repBuildFlat()`で1つの配列（`repFlat`）に平らに並べてから`renderRepAll()`で描画する。
  どの固まりを見ているかだけ分かるよう、印字例の中に控えめな見出しを挟む（後述の`repBannerHtml()`）。
- **印字例（`#rep-sample`）は白黒の印刷物そのものに見えるようにする**（利用者の指定：
  「デジタルチックな画面というよりは、もう少し印刷物のイメージで」）。薄いグレーの台紙
  （`.rg-sample-wrap`）の上に、白いレシート用紙（`.rg-sample`、`max-width:560px`中央寄せ、
  薄い影）が乗っている構図。文字は色を使わず白黒のみ、押せる値は薄い下線だけで示す。
- **各固まりの見出しは、利用者が添付した実機印字の写真をそのまま再現する**（`repBannerHtml()`）：
  「■を敷き詰めた行 → ■で挟んだ見出し文字 → ■の行」の3行。■の行は`repeating-linear-gradient`で
  敷き詰めており、幅が変わっても崩れない。
- 画面は1枚のカード：左に印字例（`#rep-sample`、縦に全文）、右に説明（`#rep-detail`）と
  いま指している固まりの項目一覧（`#rep-fields`）・注意書き（`#rep-notes`）。
- **2段階で読める**のが要点：
  1. **行**にマウスを乗せる → その行の説明（`repShowLine()`。`line.desc` ＋ あれば`line.code`）
  2. **値**にマウスを乗せる → その項目だけの詳しい説明（`repShowTok()`。`tok.k`の項目名、または`tok.d`）
  どちらも説明の先頭にどの固まりのものかを出す（`.rg-d-blk`）。
  **スマホにはhoverが無いため、`mouseover`と`click`の両方を同じハンドラにつなぐ**（`wireRepEvents()`）。
  通しで出しているので、**一度指した説明はそのまま残す**（マウスが外れても消さない）。
- 記号（A・B・C…）のある固まりでは、値の上に記号を小さく出し（`.rg-key`）、
  値と「項目一覧」の行が**相互にハイライトで連動する**（`repHlKey(si, k)`）。
  **連動は同じ固まりの中だけ**に限る（章をまたいで同じ記号が光ると別物を指してしまうため）。
- 右側の項目一覧・注意書きは、**いま指している固まりのものだけ**を出す（`repShowSideFor(si)`）。
- **印字例の桁位置（`tok.p`）は元Excelの列位置をそのまま使う。** 実機のレポートは項目どうしが
  隙間なく並ぶ場所があるため（例：最終接続日時と現メニューバージョン）、桁がずれると
  「どの位置が何の値か」が分からなくなる。等幅フォント＋`white-space:pre`＋`repWidth()`
  （全角を2桁で数える）で実物と同じ桁に並べる。隣り合う値は1つおきに背景の濃さを変えて区別する。
- **狭い画面では「説明」を印字例より上に出し、画面の上端に貼り付ける**（`.rg-detail-wrap`の
  `order:-1`＋`position:sticky`、`.rg-side`は`display:contents`）。**広い画面でも、stickyにするのは
  `.rg-detail-wrap`だけ**（`.rg-side`全体には付けない。項目一覧が長い操作で`.rg-side`の高さが
  画面を超えると、sticky要素の追従が途中で外れる不具合が実際に発生したため）。印字例が長いので、
  下の方の値をタップしたときに説明が画面外だと読めないため。

## 5. 画面3: 設定

設定タブは**シンプルさを優先**し、常時表示は最小限のカードのみとする。使用頻度の低い項目は
「詳細設定」1枚のアコーディオンにまとめ、既定は閉じておく。

| 表示 | カード |
|---|---|
| 常時表示 | 管理者ロック＋共有設定の状態（`#lock-card`、5.0参照） |
| 常時表示 | 業態ごとの定型文・時間帯（並び替え可） |
| 常時表示 | よく使う文（定型フレーズ） |
| **折りたたみ**（既定は閉） | 詳細設定 ＝ 共通設定 ＋ 作業当日の連絡文の目印 ＋ 業態・店舗ごとのGoogle Chat URL ＋ Googleカレンダー連携（停止中） |
| 常時表示 | 共有設定の保存（5.6参照） |
| 常時表示 | アプリとしてインストール（`#install-card`、5.7参照） |

業態・詳細設定の開閉は、業態の時間帯アコーディオンと同じ仕組み（`.gy-item`/`.gy-head`/`.gy-body` と
`toggleGy(id)`）を再利用する。詳細設定は固定で `gy-advanced` とする。

### 5.0 管理者ロック

- **設定の変更は管理者だけが行う。** 設定タブは既定でロックされ、`#pane-set` に `locked` クラスが付く。
  ロック中はCSSで、設定カード内の入力・選択・ボタンを操作不可（`pointer-events:none` ＋ 半透明）にする。
- **パスワードの平文は `index.html` に書かない。** `verifyAdminPassword(v, cb)` が次の順で照合する。
  1. **`admin-auth.php`**（あれば）へ `{password}` をPOSTし、`{"ok":true|false}` の返答に従う。
     パスワードは `config.php` の中だけにあり、ブラウザへは一切送られない（**推奨・最も安全**）。
  2. 無ければ **`config.json`** の `adminPasswordHash`（SHA-256。ソルトは `ADMIN_SALT` = `'oes-calendar:'`、
     つまり `sha256('oes-calendar:' + パスワード)` の16進64桁）と照合する。起動時に `loadAdminConfig()` が読み込む。
  3. `config.json` も無ければ、組み込みの `ADMIN_HASH_FALLBACK`（初期パスワードのハッシュ）と照合する。
  1が404等で失敗した場合は `adminConfig.useEndpoint = false` にして以降は試さない。
  `file://` で開いた場合は1・2を行わず3のみ。
- SHA-256は外部ライブラリを使わず `sha256Hex()` で実装する（`crypto.subtle` は `https://` でないと使えないため）。
- 照合が通ると `sessionStorage`（キー `oes-calendar-admin-unlocked`）に解除状態を持つ（ブラウザを閉じると再びロック）。
  **「保存してロック」（`lockSettings()`）でいつでも戻せる。** ボタンは`#lock-card`の上部（`#btn-lock`）と、
  「共有設定の保存」カードの下部（`#btn-lock-bottom`）の2箇所にある（どちらも解除中だけ表示、
  同じ`lockSettings()`を呼ぶ）。名前が示すとおり、**ロックする前に必ず`saveSharedSettings()`を呼んで
  共有設定を保存する**（変更を保存し忘れたままロックしてしまう事故を防ぐため。以前は保存せずロックする
  だけの「ロックする」という名前だったが、利用者の指定でこの動作と名前に変更した）。
- 入力された平文は `adminPw` に保持し、`settings-save.php` / `manual-upload.php` への
  POSTに使う。**`sessionStorage`（キー `oes-calendar-admin-pw`）にも保持する**（利用者の指定。
  ロック解除中に画面を開き直しても＝PWAの再起動等でも毎回パスワードを聞き直されないようにするため。
  `restoreAdminPw()` が起動時、解除状態が残っているときだけ読み戻す）。ブラウザのタブを閉じるか
  `lockSettings()` を呼ぶと両方消える。`sessionStorage`が使えない環境などで読み戻せなかった場合のみ、
  `currentAdminPw()` が保存時に一度だけ聞き直す。
- **ロック中でもできること**: 設定内容の閲覧、折りたたみの開閉、「共有設定を再読み込み」（`#lock-card`内）、
  「アプリとしてインストール」（`#install-card`）。これらは管理者以外にも必要なため、ロック対象から除外する。
- 変更系の関数（`addGyotai()` `moveGyotai()` `removeGyotai()` `addPhrase()` `movePhrase()` `removePhrase()`
  `addStoreChat()` `removeStoreChat()` `importSettings()` `resetSettings()` `saveSharedSettings()`）には
  `requireAdmin()` を入れ、CSSをすり抜けた場合にも変更されないようにする。
- **`admin-auth.php` を使わない場合、`index.html` や `config.json` から読めるのはハッシュだけで平文は分からないが、
  総当たりまでは防げない**（画面の誤操作防止が主目的）。厳密に制限したい場合は `admin-auth.php` を置くか、
  `deploy/.htaccess.sample` のBasic認証を併用する。
- パスワードの変更: PHPが使える場合は `config.php` の `admin_password` を書き換えるだけ。使えない場合は
  `deploy/make-hash.html` を**手元のブラウザで**開いて新しいハッシュを作り、`config.json` を差し替える
  （`make-hash.html` はサーバーに置かない）。

### 5.1 業態ごとの定型文・時間帯
- 業態: 業態名 / タイトル書式（空欄なら共通設定）/ **注意事項（`g.notes[]`、複数登録可）** / 時間帯（1件以上）。
- 時間帯: 名称 / 開始 / 終了 / 定型文。
- 「＋ 業態を追加」「＋ 時間帯を追加」「削除」。業態も時間帯も最低1件は必要。
- **並び替え**: 各業態の見出しにある「↑」「↓」（`moveGyotai(i, d)`）で順番を入れ替えられる。
  **この並び順がそのままカレンダー画面①の業態プルダウンの順番になる。**
- **注意事項**（`g.notes[]` = `{id, place, text}` の配列）: 「＋ 注意事項を追加」（`addGyNote(gid)`）で
  1件ずつ追加し、各行は「表示する欄」の選択（①入店連絡／②中間報告／③退店連絡、`setGyNotePlace()`）と
  自由記述のテキストエリア（`setGyNoteText()`）、削除ボタン（`removeGyNote()`）を持つ。
  報告のための写真の撮り方・撮影する項目などを列挙しておく用途を想定しており、複数登録できる。
  作業当日タブで業態を選んだときに、選んだ`place`と同じ欄にそのまま表示され（4.1.1節）、
  空欄なら作業当日タブには何も表示されない。

### 5.2 業態ごとの手順書・資料（画像・PDF）

- `g.manuals[]` = `{id, name, type, url, size}` の配列。実体のファイルは `settings.json` には含めず、
  サーバー上の `manuals/` フォルダに保存し、`settings.json` には参照（ファイル名・種類・サイズ・URL）だけを持つ。
- **アップロード・削除ができるのは管理者だけ**（`requireAdmin()`で二重にガード）。
  ロック解除中に使うパスワード（`adminPw`）は`sessionStorage`にも保持しており、画面を開き直しても
  （PWAの再起動など）ロックが解除されたままなら、アップロードのたびにパスワードを聞き直さない
  （5.5.1節・9-2節参照）。
- 各業態の中にある「＋ ファイルを追加（画像・PDF）」（`addGyManualClick(gid)`）を押すとファイル選択が開き、
  選ぶと `uploadGyManual(gid, file)` が管理者パスワード付きで `manual-upload.php` へアップロードする。
  成功すると一覧（サムネイル・ファイル名・サイズ・削除ボタン）に追加され、`settings.json` へ自動保存される。
  **ファイル名は省略せず全文を折り返して表示する**（設定画面の`.gyman-name`・作業当日タブの`.dm-name`
  どちらも`word-break:break-all`。以前は`.dm-name`だけ`max-width:180px`で省略していたが統一した）。
- 対応形式は画像（jpg/png/gif/webp）とPDF、**1件30MBまで**。クライアント側でも簡易チェックするが、
  実際の検証はサーバー側（`manual-upload.php` が `finfo` でファイルの中身を見て判定）で行う。
- 削除（`removeGyManual(gid, mid)`）は確認ダイアログの後、一覧と `settings.json` から即座に取り除く。
  サーバー上の実ファイルの削除は `manual-delete.php` へ依頼するが、失敗しても一覧には影響しない
  （孤立したファイルが1つ残るだけで実害がないため）。
- 作業当日タブでは、業態を選んだ時点（連絡文を作る前でも）で内容が決まり、「この内容で連絡文を作る」
  ボタンの下・「クリア」ボタンの上に一覧表示される。タップ（クリック）すると`manualHref(m)`が
  種類ごとに決めたURLへ`openManualWindow()`（`window.open()`）経由で遷移する（4.1節参照）。
- **PDFは`manual-view.php`を経由し、ダウンロード形式（`Content-Disposition: attachment`、
  `filename*=UTF-8''...`で日本語ファイル名も維持）で渡す。** ホーム画面から起動したPWA
  （WebAPK）の中でPDFをその場で開こうとすると、Androidの仕様で同一オリジンのページがアプリ内に
  留まってしまい、`window.open()`で別ウィンドウを試みても改善しないという不具合が報告されたための対策。
  ダウンロードとして渡せばAndroid側の「ダウンロード完了→開く」の流れに乗り、Acrobat Readerなど
  端末の既定のPDFアプリで開ける。画像はこの対象外（`m.url`をそのまま直接開く。画像はどのブラウザでも
  問題なく表示でき、外部アプリへの受け渡しが不要なため）。
  `manual-view.php`は`?file=<manuals/内のランダムなファイル名>&name=<元のファイル名>`を受け取り、
  `file`は`basename()`でパス操作を防いだ上で`manuals/`フォルダ内のみ参照する。認証は不要
  （一覧に出ているファイルをそのまま渡すだけで、`manuals/`への直リンクと実質同じ扱いのため）。
- **`manual-upload.php` が置かれていない・PHPが使えないサーバーでは利用できない**
  （`settings-save.php` と違い、ダウンロード＋FTPアップロードのような代替経路は無い）。
  その場合はアップロード時にエラーメッセージで案内する。
- `manual-upload.php` / `manual-delete.php` / `manual-view.php` はリポジトリの直下（index.htmlと同じ階層）
  に置いてあり、手動でのコピー・リネームは不要（配布ZIPを展開すればそのまま使える）。
  `manual-upload.php` / `manual-delete.php` のパスワードは `settings-save.php` と同じ `config.php`
  （秘密情報のため`deploy/`に置き、手動で設置する）から読み込んで照合する
  （`manual-view.php` はファイルを渡すだけで認証は不要）。
  `manual-upload.php` は保存先の `manuals/` フォルダを初回アクセス時に自動作成し、
  中に実行不可化用の `.htaccess` も自動生成する（アップロードされたファイルの中でスクリプトが
  実行されないようにする多層防御）。保存ファイル名は元のファイル名を使わずランダムな名前にする。
- **`post_max_size` 超過時の特別な扱い**: サーバーの `post_max_size`（PHP設定）を超えるサイズの
  リクエストを送ると、PHPはエラーを出さずに `$_POST` と `$_FILES` を丸ごと空にする。
  これを見分けずにいると、パスワードが正しくても「パスワードが違います」という紛らわしい
  エラーになってしまう（実際に発生した不具合）。そのため `manual-upload.php` は、
  パスワード照合より**先に** `$_SERVER['CONTENT_LENGTH']` と `ini_get('post_max_size')` を比較し、
  超過が疑われる場合は上限値を含む具体的なメッセージを返す。`upload_max_filesize` 超過
  （`UPLOAD_ERR_INI_SIZE`）も同様に専用メッセージにする。`deploy/.user.ini.sample` を
  `.user.ini` として置くと、PHP-FPM環境ではこのフォルダだけ上限を引き上げられる。
  **ただしPHPがApacheモジュール（mod_php）として動くサーバーでは `.user.ini` は効かない**
  （PHP_INI_PERDIRの一部設定はCGI/FastCGI経由でのみ読み込まれる仕様のため）。その場合は
  `deploy/.htaccess-upload-limits.sample`（`<IfModule>`で囲んだ`php_value`。mod_php向け）を試す。
  どちらが効くかはサーバーによって違うため両方の案内をする（`.user.ini`のほうが安全なので先に）。
  実際に効いている値は`manual-upload.php`をGETすると分かる（下記5.5.2参照）。

### 5.5 共有設定の保存（全員で同じ内容を使う）

- **保存場所は index.html と同じ場所の `settings.json` 1つだけ。** 全員がここから読み込む。
- 起動時に `loadSharedSettings()` が `fetch('settings.json?t=…')` で取得し、`normalizeSettings()` を通して適用、
  同時に `localStorage`（キー `oes-calendar-settings-v1`）へ控えを残す。取得できない場合は
  控え → 初期設定の順にフォールバックし、状態を `#shared-status` に表示する。
  `file://` で直接開いた場合はブラウザの制限で取得できないため、試行せず案内だけ出す。
- 「共有設定を再読み込み」（`reloadSharedSettings()`）でいつでも取り直せる（ロック中でも可）。
- 「共有設定を保存」（`saveSharedSettings()`、管理者のみ）の動作:
  1. `settings-save.php`（任意設置）へ `{password, settings}` をPOSTし、成功すればサーバー上の
     `settings.json` が更新される（＝その場で全員に反映）。
  2. エンドポイントが無い・失敗した場合は `settings.json` をダウンロードする。
     **index.html と同じ場所へFTPでアップロードすれば同じ結果になる。**
- 「ファイルから読み込む」（`importSettings()`）と「初期設定に戻す」（`resetSettings()`）も管理者のみ。
  読み込み時は `normalizeSettings()` で検証・補完し、壊れたファイルは読み込まない。
- `settings-save.php` はリポジトリの直下（index.htmlと同じ階層）に置いてあり、手動でのコピー・リネームは
  不要（配布ZIPを展開すればそのまま使える）。パスワードは `config.php`（秘密情報のため`deploy/`に置き、
  手動で設置する）から読み込んで照合し、一時ファイル経由で `settings.json` を書き換える。
  PHPが使えない場合はこのファイルが存在しても機能せず、上記2の手順（ダウンロード＋FTP）で運用する。

### 5.5.1 未共有の変更の検知と自動保存

- 管理者が設定を変更すると `markSharedDirty()` が `sharedState.dirty` を立て、設定タブの先頭に
  未共有バナー（`#dirty-bar`）を表示する。「今すぐ全員へ共有する」ボタンから保存できる。
  未共有のままページを離れようとした場合は離脱確認を出す。
- 起動時に `probeSaveEndpoint()` が `settings-save.php` へ空のJSONをPOSTし、応答から可否を判定する。
  「パスワードが違います」等のJSONが返れば利用可、`<?php` がそのまま返ればPHP未実行、
  `config.php がありません` なら設定ファイル欠落、404なら未設置、と区別する。
- 利用可と判定された場合のみ、設定変更の1.5秒後に**自動でサーバーへ保存する**（押し忘れ防止）。
  利用不可の場合は自動保存せず、バナーで「保存してFTPアップロードが必要」と案内する。
- 保存に成功すると `dirty` を解除し、ダウンロードにフォールバックした場合は
  「アップロードが済むまで未共有」として `dirty` を維持する。

### 5.5.2 サーバーの状態をチェック（診断）

- 設定タブの `#diag-card` →「チェックする」（`runDiagnostics()`）で、次を順に確認して
  ✅ ⚠️ ❌ と対処方法を日本語で表示する。**ロック中でも実行できる**（管理者以外の端末から
  原因を確認する用途があるため、`#lock-card` `#install-card` と同様にロック対象から除外する）。
  1. `https://` で開いているか（`file://` の場合はその時点で終了）
  2. `settings.json` が取得できるか。取得できた場合は**業態の並び順**とサーバー上の更新日時を表示する
     （PCとスマホで見比べれば、保存し忘れかどうかがすぐ分かる）
  3. `settings-save.php` が使えるか（使えない理由も表示）
  4. 管理者パスワードの設定ファイル（`admin-auth.php` / `config.json`）の有無
  5. `manifest.json` の取得と、そこに書かれたアイコンが全て取得できるか
  6. `sw.js` の取得と Service Worker の登録状態
  7. **手順書・資料アップロードの上限**: `manual-upload.php` を**GETで**呼び、返ってくる診断用JSON
     （`post_max_size` / `upload_max_filesize` / `sapi` / `max_bytes`）を見て、サーバーの上限が
     アプリの上限（`MANUAL_MAX_BYTES`、既定30MB）より小さければ警告し、`.user.ini`
     （PHP-FPM向け）または`.htaccess`（mod_php向け）での引き上げ方を案内する
     （`manual-upload.php`が無い場合はその旨を表示。使わない機能なら無視してよい）。
  8. インストール状態（スタンドアロン起動中か／`beforeinstallprompt` を受け取っているか）
- `loadSharedSettings()` の成功時は `#shared-status` にも業態の並び順と更新日時を出す。

### 5.5.3 アプリインストールへの導線

- 画面最下部（コピーライトのすぐ上）に、控えめな小さいテキストリンク「アプリインストールはこちらから」
  （絵文字や色付きボタンにはしない。タップ領域のみ34px以上を確保する）（`.install-link` →
  `openInstallHelp()`）を常時置く。どのタブからでも到達できる。
- `beforeinstallprompt` を受け取っていればそのままインストールダイアログを出す。
  すでにスタンドアロン起動中なら「すでにアプリとして起動しています」と知らせる。
- どちらでもない場合は、UAから iPhone / Android / パソコン を判定して、その端末の手順をモーダルで案内し、
  「設定を開いてチェックする」から診断（5.5.2）へ誘導する。

### 5.6 アプリとしてインストール

- ブラウザの`beforeinstallprompt`イベントを受け取れた場合だけ、「📱 アプリとしてインストール」ボタン
  （`#btn-install-pwa`）を表示する（既定は`hidden`）。イベントは`preventDefault()`した上で`deferredInstallPrompt`
  に保持しておき、ボタン押下時（`installPwa()`）に`deferredInstallPrompt.prompt()`を呼んでインストール
  ダイアログを出す。選択が終わったら（`userChoice`解決後）ボタンを再び隠す。
- `appinstalled`イベントでも同様にボタンを隠し、トーストで案内する。
- このイベントに対応しないブラウザ（iOS Safariなど）ではボタンは常に非表示のままとし、代わりに
  「ブラウザのメニューから『アプリをインストール』または『ホーム画面に追加』をお試しください」という
  案内文と、`manual.html`（操作マニュアル）へのリンクを常に表示する。

## 10. 認証・配置

- 配置: ドキュメントルート配下に `index.html` / `manual.html` / `assets/` / `settings-save.php` /
  `admin-auth.php` / `manual-upload.php` / `manual-delete.php` / `manual-view.php` を同じ階層で置く
  （配布ZIPを展開すればこの5つのPHPファイルは最初からこの階層に入っているので、手動でコピー・
  リネームする必要はない）。共有設定を使う場合は同じ場所に `settings.json`（アプリが書き出したもの）を置く。
  PHPが動くサーバーであれば `settings-save.php` によりアプリの「共有設定を保存」からサーバーへ
  直接保存でき（`settings.json` を書き込むためフォルダに書き込み権限が必要）、
  業態ごとの手順書・資料（画像・PDF）機能も `manual-upload.php` / `manual-delete.php` / `manual-view.php`
  により使える（アップロードしたファイルを保存する `manuals/` フォルダをこのスクリプトが自動で作成するため、
  設置場所に書き込み権限が必要）。
  ただし、いずれもパスワード照合には**秘密情報を含む** `config.php`（または`config.json`）が必要で、
  これらは自動配布の対象にせず `deploy/` フォルダのサンプルを元に**手動で1回だけ**用意する
  （`deploy/config.php` → `config.php`、または `deploy/config.json.sample` → `config.json`。
  一度設置すれば、以降のZIP更新で上書きされることはない）。
- Basic認証を使う場合は `deploy/.htaccess.sample` を参照（`AuthUserFile` は配置先の絶対パスに書き換える）。
- 認証情報はリポジトリに含めない。

## 11. 既知の制約

- 登録リストはリロード・タブを閉じると消える（未登録の予定があるときは離脱確認を表示）。
- 共有設定（`settings.json`）は静的ファイルとして誰でも読める。秘密にしたい情報（Chatの内部URLなど）を
  入れる場合は、`deploy/.htaccess.sample` のBasic認証などでフォルダ全体を保護すること。
- 管理者パスワードは `admin-auth.php` を置かない限り、ハッシュがブラウザから読める状態になる
  （平文は分からないが総当たりは防げない）。設定画面の誤操作防止が主目的であり、厳密なアクセス制御ではない。
- PWAは `https://` 配信でないとAndroidで独立したアプリ（WebAPK）にならず、アイコンにChromeのマークが付いた
  ショートカットになる。また `manifest.json` `sw.js` `icon-*.png` を置き忘れた場合も同様。
- `settings.json` の読み込みは `file://` では動かない（ブラウザの制限）。サーバーに置いて使うこと。
- `localStorage` が使えない環境（シークレットモード等）では設定が保存されない。動作自体は初期設定で継続する。
- 外部APIは、Googleカレンダー連携を設定した場合の Apps Script のURLのみ（未設定なら通信は一切発生しない）。
- Google Chat への自動送信は未実装（Incoming Webhookは Google Workspace 必須かつブラウザから直接POSTできないため、中継が必要になる）。「Chat」ボタンはあくまで該当店舗のChat画面を開くだけで、送信自体はコピー＆手動貼り付け。
- 業態・店舗ごとのGoogle Chat URL（`settings.storeChats`）は業態名の完全一致＋店舗名の文字列一致
  （語尾「店」補完後）で検索するため、同じ店舗を表記ゆれ（例:「渋谷駅前店」と「渋谷店」）や
  業態名の表記違いで別々に入力すると別の店舗として扱われ、URLが引き継がれない。未登録の場合は
  案内なしで一般のGoogle Chatが開くだけなので、事前に「詳細設定」から登録しておく必要がある。
- PWAの自動インストールボタンは`beforeinstallprompt`イベントに対応したブラウザ（Android Chrome/Edge等）
  でのみ表示される。iOS Safari等では表示されず、手動手順（メニューからのインストール）の案内のみになる。
- コピー機能は `https://` 配信が確実。非セキュアな環境では `execCommand` によるフォールバックで動作する。
- ICSインポートは確認なしで一括登録されるため、取込前の確認が必要。
- 業態ごとの手順書・資料（画像・PDF）のアップロード・削除・PDFの表示（`manual-view.php`）は
  対応するPHPファイルが置かれたPHPサーバーでのみ使える。`settings-save.php` と異なり、
  ダウンロード＋FTPアップロードのような代替経路は無いため、PHPが使えないサーバーではこの機能自体を
  利用できない。
